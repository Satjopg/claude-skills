# 構造を点検する

## 役割

動作の正しさの上に構造の正しさを積む。対象のPRやbranchが動く事は前提にし、その分け方が後の変更に耐えるかを見る。

- 判定し、直す案と決めごとを出して止まる。実行は「実行に移る時」の手順で、ユーザーが決めごとに答えてから
- 動作の正しさ(bug・脆弱性)は見ない。レビュアーの理解を速くするための説明もしない
- 「構造の正解」はrepo共通のルールではなく、このskillが持つ基準。報告の中でそれを一般論のように書かない

## 範囲を決める

PRやbranchの差分に、ユーザーが指定した概念の範囲を重ねる。差分には複数の機能が混ざる事が多く、全部を一度に見ると結論がぼやける。

- 差分の外にある既存コードは、依存先・呼び出し元・同型の既存機能として読む。差分の中だけでは依存の向きも影響範囲も分からない
- 範囲外と決めた物は、報告の「対応しない事」に理由と一緒に残す。別の文脈で進行中なら、その置き場を示す
- 差分を読む前に、変更の目的と、次にその領域へ入る予定の改修を掴む。PR本文・対話コンテキスト・設計ページ・コードパトロールの指摘が当たり先になる。予定が無ければ、観点3のシナリオは仮定で置き、仮定である事を報告に書く

## 5つの観点

### 1. 概念とモジュールの対応

不変条件(常に成り立っていなければならない事)を列挙し、主語で束ねて概念を取り出す。概念はコードの名前からではなく、守るべき事から逆算する。

- 一緒に守る理由と別々に変える理由を見る。不変条件を一緒に守るデータ(モデル)と振る舞いがまとまっているか、独立に変えたい責務が分かれているか
- 「まとめて守る単位」を見つける。1つのトランザクションや1つの処理の中で、不変条件を全部守りきれる範囲。その単位の中の不変条件が、unique index・トランザクション・暗号化などどの仕掛けで守られているかまで確かめる
- 独立した複数の単位から必要な情報を集め、判定と更新を調整する責務は、ユースケース層に置く方針で評価する

### 2. 依存の向き

対象と周辺の依存関係を確かめ、向きを見る。

- 上向きの辺(下の層が上の層を読む)と循環が無いか。型だけの依存と実行時の依存は分けて数える。循環や層違反の結論はこの区別で変わる
- 層が知ってよい事の線引きを守っているか。例えば、規則を判定する層はHTTPのステータスを知らない
- 各入口が同じ組み立てを自前で繰り返しているなら「窓口が無い」と読む。辺の本数と、組み立ての複製という実装上の事実を、分けて書く

### 3. 影響範囲と場当たり性

変更シナリオを列挙し、各シナリオで触る場所を特定する。シナリオは予定される改修から作り、無ければ仮定で置く。消す予定の概念があれば、消すシナリオも含める。

- 変更の理由ごとに、触る場所が関連する責務の流れに閉じているか。複数の流れに及ぶなら、各場所を変える理由を説明できるか。説明できずに散るのが場当たり
- 既存ファイルへの追加が、そのファイルの責務に収まっているか
- 消す予定の概念は、消す時の手数(削除だけで済むか)を主な基準にする。消しやすければ、整った置き場に出す手数は払わない
- 変更の順番に依存がある時、その順序を何が保証しているかを確かめる。暗黙の並び順だけに頼っていないか

### 4. ステートレス性

関数が呼び出しをまたいで状態を抱えず、必要な状態と外部依存を外から渡せる形かを見る。注入した状態と外部依存をテストで制御できるのが基準。

- 環境変数・モジュール変数・共有クライアント・現在時刻・乱数などの隠れた状態が、引数で注入されているか。注入されていなければ、状態の所有者がどこで、関数がそれをどう読んでいるかを書く
- 注入されていない物を注入に直すか、テストで固定したまま置くかは決めごとに置く。テストが今それをどう固定しているかを、選択肢の材料として添える

### 5. repoの作りとの整合

対象のPRがrepoの既存の作りにどう収まっているか、直す案がそこから外れないかを見る。正しい構造でも、repoの中で浮く置き方は後の作業者が倣えない。

- 層を新設するなら、既存の同じ層の作り(ファイルの粒度・indexの有無・classの有無・置く階層)に合わせる
- 配置や粒度の慣習と、引き継ぐべき設計判断は分けて評価する。慣習は既存に合わせる。設計判断は、同型の既存機能でその判断が未解決の問題の原因になっているかを見て、引き継ぐか決める
- 新しい型を持ち込む時は、それがその領域で初めてである事を報告に書く

## 報告の書き方

[TEMPLATE.md](TEMPLATE.md) の形でチャットに出す。節の順番はTEMPLATEのまま使い、節を足さない。本文は重要な順に目安の件数へ収め、超過分は件数・場所・結論への影響を1行で要約する。

- 結論を先に1文で書く。確認できた範囲に応じた結論にする
- 抽象語は言い換える。集約は「まとめて守る単位」、アダプタは「〜との橋渡し」、ドメイン層は「規則を守る場所」のように、その場の対象で言う。抽象語のままだと概念が伝わらない
- DBのレコードやコレクションは比喩でなく具体名で呼ぶ
- 直す案は、対応するギャップと期待する効果、前後の形(どこに何を置くか・変えない物)まで書く。「分けた方がよい」で止めない。案によって新しくできる経路(例外が届く先が増える等)も挙げる。PRの積み方は分割が要る時だけ書く
- ユーザーが決める事は推測で埋めず、「決めごと」に番号を付けて置く。選択肢と、それぞれで触る場所・責務・依存の違いを添える
- 読まなかった当たり先と、残る不確実性が結論にどう効くかを「確かめられなかった事」に書く。「見ていない」を「無い」に縮めない

## 実行に移る時

ユーザーが決めごとに答えて実行を指示したら、実装の前に計画を出して承認を得る(Claude Code では plan mode)。計画は決めごとの答えと直す案から作り、答えで前提が変わっていないかを確かめる。別のsessionで実行する時は、残した報告を読んでから計画を出す。
